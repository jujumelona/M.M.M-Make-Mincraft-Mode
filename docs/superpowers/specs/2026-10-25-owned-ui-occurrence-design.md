# Build a requested UI occurrence before binding its gameplay listener

The uploaded production run at `7e356d79a504` declines an arrival callback for
an explicit user initiation, finds no authored occurrence method, and aborts
before generating that method. Source-owned routing therefore still requires
the custom feature to exist before it can implement the custom feature.

Keep the existing inspected callback and Mixin routes. When neither represents
the occurrence, a behavior with an explicit player selection/confirmation may
use the existing Typed Action form, validation and command transport. The host
generates its concrete server event, input codec, client form and startup
registration before the gameplay listener is compiled. Only action labels and
bounded player input metadata are model-authored. The server owns the actor;
client inputs never establish currency, permissions or world facts.

This is an implementation of a requested interaction, not a substitute trigger
for a passive world event. An exact quote of the original active trigger is
required. Unsupported/passive occurrences continue to require a genuine source
owner. No theme names or prompt-specific gameplay are built into the host.

Plans are side-effect-free. Generated files and manifest entries are installed
only after all listener bodies have been authored. Replayed registration proof
must reconstruct the producer and check its exact files and startup entries.
Neither a receipt nor a compiling form certifies gameplay or Minecraft runtime.

Validation covers actual action submission into a listener, rejected inputs,
false results, independent user actions, passive triggers, failed authoring,
manifest preservation, idempotence and changed producer bytes.
